Mapping: Django -> .NET (high level)
------------------------------------
- Django Model -> Domain Entity (Domain/Entities)
- Django Serializer -> DTOs (Application/DTOs), use AutoMapper profiles
- Django View/ViewSet -> API Controllers (API/Controllers) that call Application services
- Business logic in serializer.save() or model.save() -> Application Services (Application/Services) or Domain methods
- Django ORM -> EF Core (Infrastructure/Data)
- Authentication (DRF SimpleJWT) -> ASP.NET Core JWT Bearer (with ASP.NET Identity or custom user store)
- Middleware -> ASP.NET Core middleware pipeline (Global exception handler + Serilog)

Authentication & Authorization mapping
------------------------------------
- Use ASP.NET Core Identity for user persistence (or custom IUserStore if you prefer to map Tenant onto IdentityUser). Recommended: extend IdentityUser to TenantUser.
- Configure JWT Bearer authentication using Microsoft.AspNetCore.Authentication.JwtBearer and issue tokens via a TokenService. Optionally use refresh token storage in DB (like `AuthToken`) to support revocation/blacklist behavior.
- Map Django cookie-setting logic (if required) to issuing HttpOnly cookies in .NET as needed.


Payment gateway & webhook
-------------------------
- Implement IPaymentGateway interface and Paystack adapter (InitializeTransactionAsync, VerifyTransactionAsync, HandleWebhookAsync).
- Webhook endpoint must verify signature (HMAC SHA512) using the configured secret (same as Django code). Ensure immediate idempotency checks and safe handling of concurrent webhook calls.


EF Core (Infrastructure/Data) recommendations
--------------------------------------------
- Use separate project `Infrastructure` with `Data` folder containing `AppDbContext : DbContext`.
- Configure entities with Fluent API in `EntityTypeConfiguration<T>` classes for:
	- Unique constraint on (PropertyId, RoomNumber) for Unit
	- One-to-many and one-to-one relationships
	- Indexes on Payment.Reference unique, TenancyAgreement lookups
- Consider using `decimal` for currency in C# if you later need fractions; currently amounts are integer smallest unit (pesewas) and can map to `int` or `long`.


Data migration / seeding strategy
-------------------------------
- Option A (recommended for parity): Use the existing SQLite DB (`rent_in/db.sqlite3`) as the source-of-truth for data. Write a small data import tool that reads from SQLite (via EF Core SQLite or direct SQLite connection) and writes to the new DB (Postgres or SQL Server). This avoids manual data loss.
- Option B: Recreate schema in EF Core and re-seed essential test data using seeders.

Edge cases & important notes
---------------------------
- Nested serializer logic in Django (for example PaymentSummary returning nested payments) should be mapped to DTOs and service-layer queries (include related entities to avoid N+1).
- Model.save() logic in Django (e.g., Tenancy_Agreement.save computes end date, PaymentSummary.save aggregates payments) should move into Application services or Domain methods called by services; avoid putting heavy logic in DbContext save triggers.
- Unique constraints and on-delete semantics must be explicitly specified in EF Core Fluent API to match Django behavior.
- Authentication: if you rely on Django's `AuthToken` table for token invalidation, replicate a refresh-token / blacklist pattern in .NET (store hashed tokens, support revocation).

Database selection (confirmed)
--------------------------------
You requested: development on SQLite and production on PostgreSQL. The guidance below assumes this setup.

Dev (SQLite)
- Keep the existing `rent_in/db.sqlite3` for development and quick iterations.
- Use EF Core SQLite provider for local development and testing: `Microsoft.EntityFrameworkCore.Sqlite`.

Production (PostgreSQL)
- Use PostgreSQL in production and use the Npgsql EF Core provider: `Npgsql.EntityFrameworkCore.PostgreSQL`.
- Advantages: reliable migrations, support for JSONB, strong community support on Linux containers.

Data migration from existing SQLite to Postgres (recommended approach)
------------------------------------------------------------------
Option 1 — Data import tool (recommended):
  - Create a small console app or EF Core import tool in `Infrastructure/Tools/DataImporter` that:
	 1. Connects to the existing SQLite DB (use separate EF Core DbContext configured with SQLite).
	 2. Reads entities in a deterministic order (Tenant -> Property -> Unit -> TenancyAgreement -> Payment -> PaymentSummary) to preserve FK references.
	 3. Writes to the production EF Core DbContext configured for Postgres (or to a staging Postgres instance) in batches and within transactions.
	 4. For large datasets consider bulk operations or COPY for performance. For small projects EF Core SaveChanges() is fine.
  - Validate counts and referential integrity after import.

Option 2 — Export/Import SQL
  - Dump SQLite data to CSV and use Postgres COPY to import into tables after creating the schema.
  - This requires mapping differences (GUIDs, identity sequences) and handling unique constraints carefully.

Relationship matrix (fields, multiplicity, on-delete and nullable flags)
----------------------------------------------------------------
| From Model | FK Field | To Model | Multiplicity | OnDelete | Nullable | Notes |
|------------|----------|----------|--------------|----------|---------|-------|
| Tenancy_Agreement | tenant_id | Tenant | Many-to-One (Tenant 1 -> N Tenancy) | Cascade | False | tenant is required |
| Unit | property_id | Property | Many-to-One | Cascade | False | unit belongs to property |

| Tenancy_Agreement | property_id | Property | Many-to-One | Cascade | False | tenancy references property |
| Tenancy_Agreement | unit_id | Unit | Many-to-One | Cascade | False | tenancy references unit |
| Payment | tenant_id | Tenant | Many-to-One | Cascade | False | payments belong to tenant |
| Payment | unit_id | Unit | Many-to-One | Cascade | False | payments belong to a unit |
| Payment | tenancy_agreement_id | Tenancy_Agreement | Many-to-One | Cascade | True | optional until linked by webhook/verify |
| Tenancy_Agreement | payment_summary_id (reverse) | PaymentSummary | One-to-One | Cascade | False | PaymentSummary.tenancy_agreement OneToOne |

Notes on mapping multiplicity and cascading
- Django's default `on_delete=models.CASCADE` maps naturally to EF Core's `DeleteBehavior.Cascade` for required FKs.
- For nullable FKs (e.g., Payment.tenancy_agreement), map to `int?` or the proper nullable type in C# and configure `DeleteBehavior.SetNull` if desired, else `Cascade` if you want orphaned payments deleted.
- Ensure `Unit`'s unique constraint on (PropertyId, RoomNumber) is implemented as a unique index in EF Core.
